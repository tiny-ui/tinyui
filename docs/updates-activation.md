# 热下发的生效时机：讨论稿

- 状态：**讨论中，未定**（2026-11-23 起）。本文只记讨论到哪一步，不改变任何行为；现状以 [updates.md](./updates.md) 为准，已定的决策以 [ADR-006](./adr-006-hot-updates.md) 为准
- 来源：ADR-006 §2.3 选了「下次启动生效」，§4.3 把「无活页时立即切换」记为推迟项。这次重开的是 §2.3 整个问题
- 下次接着谈：从 §4 的待定项开始

## 1. 起因

开发与测试构建的使用者要验证一个刚发布的版本，现在得冷启动两次：第一次启动只触发检查与安装，页面已经挂在旧包上；第二次启动才选到新包。状态行（updates.md §4.7）能把它减到一次，但要人看懂状态、等它变色、点击、再手动打开，学习成本高。

目标两条：

1. 新包尽快用上
2. 不增加代码与逻辑的复杂度，最好能减

## 2. 现状梳理

一个版本从发布到被看到，经过五个环节：

| 环节 | 现在怎么做 | 耗时或人工 |
|---|---|---|
| 1. 发布 | CI 签名发到通道；晋级到正式通道是手动命令 | 分钟级 |
| 2. 检查 | 取一次指针：启动、网络失败后重试一次、回前台按间隔（默认 1 小时，开发构建可调到十秒量级）、手动（§4.6） | 自动 |
| 3. 安装 | 验签、逐文件核对、落盘，记为 `pending` | 几秒，自动 |
| 4. 生效 | `Updates` 构造时选包，整个进程不再换（§4.4） | 要一次冷启动 |
| 5. 可见 | 状态行显示版本，有版本等待生效时高亮、点击重启（§4.7） | 要人看懂、要人点 |

两次启动出在第 2 与第 4 环节是分开的。

整套机制可以拆成六个互相独立的问题：

| 问题 | 现状 | 在哪 |
|---|---|---|
| A. 何时检查 | 四种触发 | `UpdatesScheduler` |
| B. 何时生效 | 只有下次启动 | `Updates` 构造时选包 |
| C. 生效时已打开的页面怎么办 | 没有这个问题；唯一的例外是回退，出错的页面当场换回内置包重挂（§4.5） | `UpdatesPage` |
| D. 怎么让人知道 | 状态行、`status`、事件 | `UpdatesStatusLine` |
| E. 坏包怎么兜 | 页面失败即回退内置并拉黑、灰度、指针只往前、`hostVersion` 精确匹配 | `rollBack`、服务端 |
| F. 首次安装跑什么 | 内置包，构建时取该通道的当前版本（§1.4） | Gradle 插件 |

两个目标落在 B、C、D 上；A、E、F 不动。

## 3. 已定的

1. **正式构建与开发构建一起变快**，不只解决开发与测试阶段
2. **生效机制保持同一套**：不给开发构建单开一条正式用户走不到的生效路径（延续 §4.7「生效机制不为此另开一套」）

## 4. 待定的

### 4.1 生效时机（问题 B）

三个候选：

| | 甲. 启动时限时等检查 | 乙. 装好即切，只对新开的页面 | 丙. 装好即切，已打开的页面当场重挂 |
|---|---|---|---|
| 验证新版本要做什么 | 仍要冷启动一次 | 退出当前页再进；退不出去的页面（作为首屏的根页）实际还得重启 | 什么都不用做，回到前台后页面自己刷新 |
| 正式用户 | 每次冷启动首个页面多等一次指针请求，弱网等到超时；进程长活时不受益 | 无感，但同一流程里新旧页面混跑 | 见下 |
| 改动量 | 宿主几行 | 库十几行 | 库几十行，同时能删东西 |

**倾向丙，尚未确认。** 理由：

- 安装只发生在检查之后，而检查只有两个时机：启动，和回前台（距上次成功满间隔）。前台停留期间没有定时检查。所以重挂只会出现在刚启动的头一两秒（页面先显示旧版、随后刷新，每台设备每个版本一次）和离开很久再回来的头一两秒。这两个时刻用户基本还没开始操作，现有的检查时机本身就是安全点，不用另加判断
- 进程内换包并重挂，回退路径已经在做（`UpdatesPage` 把 `bundle` 换成内置包即重建引擎），这次是同一个动作的反方向
- 能删掉的：`pending` 状态、状态行的「等待生效」一行与 `onRestart`、宿主结束进程的接线。规则从「装好，等下次启动」变成「装好即生效」，概念少一个

甲的问题：每次冷启动都付出等待，却只省掉两次启动中的一次。乙的问题：退不出去的根页拿不到新包，正是最痛的那个场景。

### 4.2 丙的代价，要不要加保护

选丙之后问题 C 一并定成原地重挂。它带来四条代价，每条要不要加保护都还没谈：

1. **输入丢失**：弱网下载慢时用户可能已经开始输入，重挂后页面状态清空
2. **旧 props 给新页面**：栈里的页面带着旧版本传的 props 重挂。新版本改了页面间的参数契约时可能加载失败，而 E2 / E6 会触发回退并把这个版本在该设备拉黑（§4.5），要等下一个版本才恢复。ADR-006 §2.3 当初否掉「下次进页面」就是因为这类契约漂移；只有「回到流程起点、props 由宿主给」能完全避开，但那要库知道导航栈，或者把重建交给宿主
3. **未完成的请求丢失**：重挂时页面里在途的 `http`、`host.call` 结果没人接
4. **一个进程不再只有一个包**：遥测里的包版本会在进程中途变化。回退已经如此

丙之下「等待生效」不再出现。剩下哪些状态、点击做什么、`status` 的字段怎么收，没谈。

## 5. 考虑过、已放弃的

- 分安全点静默切换（无活页即切、后台超过若干分钟回来时重置流程）加活页计数，以及小程序式的「有更新，点击重载」提示：都要新增状态与判断，与「不增加复杂度」相悖
- 只给开发构建开进程内生效：违背 §3 第 2 条

## 6. 业界参照

| | 默认 | 立即生效的手段 |
|---|---|---|
| 微信小程序 | 异步下载，下次冷启动生效；小程序在后台约 30 分钟即销毁，冷启动很频繁 | `onUpdateReady` + `applyUpdate()`，提示由开发者自己写，多用于强制更新 |
| Expo Updates | 下次启动 | `reloadAsync()`；或启动时限时等待（`fallbackToCacheTimeout`） |
| CodePush | `ON_NEXT_RESTART` | `ON_NEXT_RESUME` 加最短后台时长；强制更新才 `IMMEDIATE` |

三家的默认都是不打扰用户。小程序体感快主要靠冷启动频繁，App 的进程常常活好几天，「下次启动」因此稀少得多，这是本框架照搬该默认后的落差所在。
