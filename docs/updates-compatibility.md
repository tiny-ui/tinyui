# 宿主加版本后页面包怎么跟：讨论稿

- 状态：**讨论中，未定**（2026-11-27 起）。本文只记讨论到哪一步，不改变任何行为；现状以 [updates.md](./updates.md) 为准，已定的决策以 [ADR-006](./adr-006-hot-updates.md) 为准
- 来源：ADR-006 §2.2 选了精确匹配的 `hostVersion`，§2.11 把「以客户端能力探测替代 `hostVersion`」记为推迟项（roadmap D 组），触发条件是「`hostVersion` 加 1 的频率重新成为负担」。这次是第一个多包宿主遇到它
- **为什么现在不定**：框架还在频繁迭代，没有稳定下来，破坏性变更还会有；这个阶段精确匹配正合适，它保护的就是「宿主会删改」的情况。兼容模型留到框架稳定之后再谈
- **目前倾向**（不是决定）：稳定之后走微信小程序的方向（§4.4）。理由两条：开发者教育成本低，「一个线上版本、最低版本加能力判断」容易讲清楚；那时框架基本完善，不太会再有破坏性变更，「只增不删」的前提自然成立
- 下次接着谈：框架稳定下来之后，从 §4.4 的未决问题开始；§3 已定的一条不依赖方向，框架侧已做

## 1. 起因

一个宿主挂着三个页面包：`login`、`orders`、`coupons`。时间线：

| 时刻 | 发生了什么 |
|---|---|
| T0 | App 1.0 上线，`hostVersion` 2。`login` 当前版本记作 v1 |
| T1 | 宿主为优惠券加了能力 `coupon.apply`，`hostVersion` 升到 3（App 1.1）。`login` 一行没改 |
| T2 | `login` 修了一处文案，出 v2，没用任何新能力 |
| T3 | `login` 开始用 3 才有的能力，出 v3 |

期望：T1、T2 时两个 App 都拿到最新的 `login`；T3 时 1.1 拿 v3，1.0 留在 v2。

现在的规则下（updates.md §1.4、§2）：

- T1：目录 3 下没有 `login`。正式包的构建失败，等 `login` 在 3 下发布并晋级；测试包回落到目录 2 的版本并警告，能打出来，但装上后去目录 3 查更新，那里是空的，`login` 之后的改动它收不到
- T2：v2 要在 2、3 下各签一次、各发一次、各晋级一次。`hostVersion` 在签名范围内，一份签好的产物只属于一个版本；`tinyui.config.json` 里只能写一个 `hostVersion`，各发一次要页面包仓自己想办法
- 这次加 1 是为 `coupons` 加的，`login` 与 `orders` 一个新能力都没用，但都要跟着做动作

ADR-006 §2.11 预期过这个动作（「B 只需把现有内容重发到新 `hostVersion`，不必重建」），但没有配套工具。

## 2. 根因

**兼容关系本身是「集合包含」，投递却用「发布位置」来表达。**

- 真实的兼容关系：包用到的东西宿主都提供，就能跑。这是一对多的，一个只用老能力的包天然能在之后只做新增的宿主上跑
- 这个事实系统里已经有，而且机器可判定：manifest 的 `requires` 记着包用到什么（build-chain.md §5.1 的硬规则保证找得全），每个 `hostVersion` 的快照记着宿主提供什么，`publish` 已经在按它核对（updates.md §1.3）
- 但投递不用这个事实。App 取包只看「这个包有没有被发布到我的 `hostVersion` 目录下」，兼容性成了发布者的一个动作，不是从包的需求推导出来的

带出的三个后果：

1. **加版本的代价落在无关的包上**：宿主每加一点东西，所有页面包都要响应一次
2. **版本号不区分「新增」与「破坏」**：`hostVersion` 是一个整数，纯新增与删改同样加 1，精确匹配等于把每次变更都当破坏性变更处理
3. **产物不能跨版本复用**：同一份字节码要进另一个版本，必须用私钥重签，只有包自己的 CI 能做

成本是「在用的宿主版本数 × 页面包数」，每次加 1 由各页面包仓各付一次。

精确匹配当初是有意选的（ADR-006 §2.2）：范围匹配在宿主删改能力时不成立，能写上界的是当初写页面的人，知道宿主后来改了什么的是改宿主的人。§2.11 也写明 `hostVersion` 已不是兼容判断的必需品，留下来只为三件事：投递分组、发布前知道目标人群有什么、同名改义的声明。下面任何方向都要对这三件事有交代。

## 3. 已定的

**测试包也失败，与正式包一致。** 当前 `hostVersion` 下取不到包，任何通道的构建都失败，不再回落到更小的 `hostVersion`。页面包在新版本下的发布先由人手动做；不加开关，不做自动重发；兼容模型不变。

理由：回落让测试包走了一条正式用户走不到的路（内置的是旧版本目录下的包，又收不到后续更新），页面包没跟上这件事被一条警告盖住，要拖到打正式包才暴露。

框架侧已实施（2026-11-27，下面第 1、2 条）；各宿主升到带这个改动的版本时生效，升之前先做第 3 条：

1. Gradle 插件 `Delivery.resolve` 去掉「取不到就把 `hostVersion` 减 1 再试」的循环。没有网络时沿用上次结果的规则保留，但只在上次结果属于当前 `hostVersion` 时沿用，否则加 1 之后的离线构建等于又回落了
2. 改 `DeliveryTest` 对应用例；改 updates.md §1.4、integration.md 里「测试包会回落」的说法
3. 各宿主升到带这个改动的版本之前，先让挂在它上面的页面包在当前 `hostVersion` 下都有版本

接受的代价：

- 宿主加 1 的分支在合入前打不了测试包，只能用页面源码现编（`tinyui.<pkg>.dir`）
- **快照上传不能排在宿主测试后面**（实施时撞上的）：宿主测试所在的模块要先取到内置包，去掉回落后，「上传等测试、测试等内置包、内置包等页面包发布、页面包发布等快照」成了环。快照只描述宿主自己，上传本不该依赖页面包；改成上传不设前置测试，快照与宿主一致由加 1 的人合入前在本地跑测试保证，冻结了对不上的快照只能再加 1（updates.md §4.1、integration.md §2.5）。更严的做法是把构造宿主与快照测试挪到不带内置包的模块，让测试不需要页面包就能跑，代价是每个宿主都要拆模块，先不做
- 加 1 的提交合入、快照上传之后，到所有页面包发完之前，主干也打不了包。宿主的 CI 若在合并请求上跑需要内置包的任务，加 1 的那次合并请求必然是红的：快照合入后才上传，页面包有快照才能发

## 4. 待定的方向

四个方向，差别只在「谁来决定某个包投给哪个 App」。

| | 谁决定 | 包发几次 | `hostVersion` 还剩什么用 | 客户端要改吗 |
|---|---|---|---|---|
| 现状 | 发布的人，手填 | 每个版本一次 | 目录名，且写进包里 | — |
| 4.1 多版本发布 | 发布工具，循环核对 | 每个版本一次，工具代劳 | 同现状 | 不用 |
| 4.2 服务端推导 | 服务端，按快照算 | 一次 | 只是目录名 | 取包路径不变，装包前的核对要调整 |
| 4.3 客户端协商 | 客户端，按自己的能力挑 | 一次 | 基本不用 | 取包逻辑整个换 |
| 4.4 微信方向 | 页面代码，运行时判断 | 一次 | 只在破坏性变更时加 | 加一条等级比较 |

### 4.1 多版本发布（精确匹配不变）

规则不变，把重复动作交给工具。两档：

- **页面包仓的 CI 写版本列表**：编译一次，按列表逐个 `tinyui bundle --host-version <n>` 签名、逐个 `tinyui publish`，每个各自过快照核对。`tinyui.config.json` 的 `hostVersion` 写列表里最小的，页面按最老的宿主写。现有 CLI 就能做，不用改框架
- **做进 CLI**：`publish` 自己找出在用的 `hostVersion`，对每个核对通过的签一份、发一份，页面包仓不维护列表。「哪些版本还在用」要有地方记

带入 §1：T1 要有人触发一次 `login` 的发布；T2 一次命令发两份；T3 工具发现 2 的快照里没有新能力，只发 3。之后要给 1.0 修问题，从旧代码拉分支，只发 2。

没碰根因：发布、存储、晋级的次数仍是版本数的倍数。只要列表里还有老版本，页面就不能用新能力，tinyui 三包也不能高过最老宿主的下限。这是 Expo 与 Shorebird 的官方做法（§6）。

### 4.2 服务端推导投递

包里不再写 `hostVersion`，签一次、上传一次、存一份。服务端维护每个 `hostVersion` 目录的指针，规则是指向「`requires` 都在这个版本的快照里」的最新一版。客户端的取包路径与现在完全一样。

带入 §1：T1 宿主上传 3 的快照时，服务端算出 v1 能跑，自动把目录 3 的指针指向 v1，`login` 的人什么都不用做；T2 发布一次，两个指针一起动；T3 发布一次，只有 3 的指针动。

- 不依赖「只增不删」：对每个版本的快照单独算，宿主删了能力，用到它的包自然投不过去
- 不动投递协议。ADR-006 §2.11 否掉 4.3 的理由是「协议一经发布不能再变」，这个方向绕开了它
- 要改：签名范围（`hostVersion` 在签名内防的是包被放进错的目录，去掉后要由客户端装包前核对 `requires` 顶上）、服务端、CLI；放弃纯静态托管，发布时服务端要计算

### 4.3 客户端协商

roadmap D 组记的方案。服务端不按 `hostVersion` 分目录，每个包一个指针，指针里是一张候选表：每个候选写着版本号与它的 `requires`。客户端从新到旧找第一个「用到的东西我都有」的版本。

带入 §1：T1 什么都不用发生；T3 表变成「v3、v2」，1.1 挑中 v3，1.0 往下挑中 v2。

能静态托管。要改投递协议与客户端，判断逻辑随 App 发出去，有问题只能随 App 修。

### 4.2 与 4.3 共同的两个问题

- **必须「能力改了就换名」**：机器只比对名字，名字没变而行为变了，旧页面会被投到新宿主。现在这种情况靠人加 1 来挡
- **给老 App 单独修问题更绕**：T3 之后从 v2 拉分支出的修复版比 v3 新、又不用新能力，按「最新且能跑」会被投给 1.1 把 v3 顶掉，得另有办法声明「这版只给老宿主」。4.1 没有这个问题

**机器核对的盲区。** `requires ⊆ 快照` 只是能跑的必要条件，不是充分条件：

1. 同名改义（updates.md §1.3：「核对的是名字，覆盖不到已有能力的参数形状与行为」）
2. 快照之外的依赖：跨包跳转的目标页（只警告）、宿主的隐式行为、跨包共用的 store key 与事件主题
3. 没人在那个宿主上跑过这一版

现在这个核对是安全网，人选了目标版本，机器拦住填错；4.2、4.3 把它升成唯一依据，漏判的后果是不崩溃的静默失效，回退接不住。要走这两个方向得补第二道保障，可选：只自动到测试通道、晋级仍由人按版本确认；把能力的参数形状写进快照（roadmap D 组「宿主契约 schema 化」）；宿主侧在新版本上把各包的关键页面真跑一遍。

### 4.4 微信小程序的方向（目前倾向）

一个包在线上只有一个当前版本，所有 App 拿同一份；宿主新增能力不让页面包重发，新老宿主的差异由页面代码在运行时判断；不想再照顾老宿主时抬高下限。

微信的原样是三件东西：基础库版本号、后台设置的「最低基础库版本」、`wx.canIUse`。它只有一个版本号，没给破坏性变更留出口，靠基础库不破坏。ADR-006 §2.2 不愿要求宿主永久保留旧能力，所以落到本框架时保留 `hostVersion` 作出口，另加一个只比大小的数（Android 的 API level 同类）：

| | 什么时候加 1 | 作用 |
|---|---|---|
| `hostVersion`（保留） | 只在删除或改变已有能力时 | 投递目录，精确匹配，同现状 |
| `hostLevel`（新增，名字待定） | 宿主每次新增能力、组件、通道、路由时 | 只用来比大小 |

同一个 `hostVersion` 内，等级高的宿主提供的东西是等级低的超集。投递路径不变；`hostVersion` 很少再加，目录实际上长期只有一个。

三方的约定：

- **宿主**：老能力不改参数、不改行为，要改就起新名字。每个等级一份快照，宿主测试加一条「本等级的快照包含上一等级的全部名字」，名字这一层的只增不删由机器守
- **页面包**：manifest 加最低等级；`requires` 分成必须的与可选的
- **页面代码**：用新能力前先判断（`host.has("coupon.apply")`），没有就走老流程；参数必须是字符串字面量，构建时据此认出可选的能力。ADR-003 与 ADR-006 提到过 `host.has()`，`tinyui-native` 里还没有

各环节：

| 环节 | 现状 | 改成 |
|---|---|---|
| 构建 | 找出用到的能力写进 `requires` | 另把出现在 `host.has` 里的标成可选，写入最低等级 |
| 发布前核对 | 用到的都在目标 `hostVersion` 的快照里 | 必须的都在最低等级的快照里；可选的至少在某一级快照里（防拼错） |
| 客户端装包前 | `hostVersion` 相等 | 再加一条：包的最低等级不高于自己的等级，否则跳过 |
| 宿主构建取内置包 | 当前 `hostVersion` 目录下没有就失败 | 规则不变，新增能力不换目录，不会再遇到空目录 |
| 晋级、回滚、灰度 | 每个 `hostVersion` 各一次 | 一次 |

带入 §1：T1 无事发生；T2 发布一次；T3 两条路，写降级（发布一次，1.0 跑老流程）或抬下限（1.0 从此停更，含问题修复）。只要老 App 还要照顾，实际只能写降级。之后给 1.0 修问题最简单，发布一次所有 App 都收到。等 1.0 的活跃占比足够低，抬下限并删掉降级分支。

代价：

- 页面要写降级分支，并在最低等级与最新等级上都测。宿主只能随 App 发版，分支可能留几个月；微信的基础库能自己推更新，老版本淘汰快，这是照搬时的落差
- 老 App 持续收到新代码，新版本在老宿主上有问题时影响全部老用户，发布要先灰度
- 抬下限是一刀切，抬了之后没法再给老 App 单独修
- 机器核对比现状弱一档：可选能力靠开发者写对降级，写漏了是静默失效
- 「改了就换名」靠纪律。与现在靠人加 1 同一个难度，出错的方向变了：现在忘了加 1 才出事，以后改了没换名才出事

「框架稳定」与「宿主自己的能力不再删改」是两件事：前者是本框架的事，后者是各个 App 的事（换了支付渠道要改能力）。保留 `hostVersion` 作出口覆盖的是后者，所以这个方向不要求宿主永不破坏。

未决问题：

1. 最低等级由工具按必须的能力自动算，还是开发者手填、工具核对。倾向自动算
2. 「可选」怎么认。同一页里出现过 `host.has("x")` 就把这一页对 `x` 的调用都算可选，规则简单，但判断了却在别处无条件调用的，机器看不出来
3. 抬下限后老 App 完全停更，要不要留一条老等级专用的维护线。留了就又回到多指针，倾向不留
4. 低于下限的 App 只是不再更新，要不要提示升级。倾向留给宿主
5. 已有宿主怎么并进新模型：哪个 `hostVersion` 作起点，等级从几开始

## 5. 考虑过、已放弃的

- **正式包也回落到更小的 `hostVersion`**：能打出包，但装上后在当前版本目录下查不到更新；要彻底就得让运行时也回落，等于改成范围匹配，回到 ADR-006 §2.2 否掉的情形。而且「正式包打不出来」这个强提醒变成一条警告
- **给回落加开关，由宿主选严格还是宽松**：同一件事留了两种行为，与「只留一种写法」相悖
- **发布方声明范围**（CodePush 的 `targetBinaryVersion`）：ADR-006 §2.2 已否，理由不变

## 6. 业界参照

2026-11-27 查各家官方文档。

| 家族 | 代表 | 宿主加版本时发布方做什么 | 主要风险 |
|---|---|---|---|
| 精确匹配 | Expo EAS Update、Shorebird | 每个在用的宿主版本各发一次 | 发布次数随版本数增长，旧版本容易漏发 |
| 发布方声明范围 | CodePush | 改范围，一次覆盖多个版本 | 系统不校验，范围写宽会落到不兼容的宿主上 |
| 下限 + 能力探测 | 微信小程序、Android、VS Code 扩展、Chrome 扩展 | 什么都不用做 | 宿主要长期守住向后兼容；低于下限的用户被挡在外面或收不到更新 |

- **Expo**：runtime version 与 update 的目标 runtime version 必须完全相等（[How it works](https://docs.expo.dev/eas-update/how-it-works/)）；理由是它描述整个 JS 与原生之间的接口（[Runtime versions](https://docs.expo.dev/eas-update/runtime-versions/)）。所查页面里没有「一次发布覆盖多个 runtime version」的命令，官方做法是每个原生版本各更新一次、把修复摘到旧分支（[best practices](https://expo.dev/blog/eas-update-best-practices.md)）
- **Shorebird**：一个 patch 只对一个 release，修三个版本就打三次（[Patch](https://docs.shorebird.dev/code-push/patch/)、[Patch several releases](https://docs.shorebird.dev/code-push/guides/patch-several-releases/)）
- **CodePush**：`targetBinaryVersion` 支持 semver 范围，`patch` 可改已有 release 的范围，兼容性完全由发布方声明（[code-push-server CLI](https://github.com/microsoft/code-push-server/blob/main/cli/README.md)）
- **微信小程序**：后台可设最低基础库版本，低于则打不开并提示更新客户端；运行时用 `wx.canIUse` 判断（[兼容](https://developers.weixin.qq.com/miniprogram/dev/framework/compatibility.html)）。基础库随客户端发版并灰度，高版本基础库跑不了低版本客户端（[基础库](https://developers.weixin.qq.com/miniprogram/dev/framework/client-lib/)）
- **Android**：`minSdkVersion` 是下限，平台改动以新增为主，旧接口弃用但不移除（[uses-sdk](https://developer.android.com/guide/topics/manifest/uses-sdk-element)）
- **VS Code 扩展**：`engines.vscode` 声明最低版本（[Extension manifest](https://code.visualstudio.com/api/references/extension-manifest)）；**Chrome 扩展**：`minimum_chrome_version`，低版本的已装用户静默收不到更新（[minimum_chrome_version](https://developer.chrome.com/docs/extensions/reference/manifest/minimum-chrome-version)）

精确匹配适合宿主接口是隐式的、没人能说清里面有什么的情形，Expo 的理由正是如此；下限模型适合宿主是「平台」的情形：接口显式、有版本、有人维护兼容承诺。本框架的宿主契约已经是显式的（快照）且机器可读（`requires`），具备后一类的前提，差的是兼容承诺，这也是文首说等框架稳定的原因。

没能核实的：

- 微信基础库「只增不删」的承诺没找到官方原文，是从它的兼容机制推出来的
- CodePush 因范围写宽而落到不兼容宿主的事故或官方警示，没找到一手来源（原 App Center 文档已下线）
- Expo「没有多 runtime 发布」是所查页面未提及，不是官方明确否认
- 应用商店、扩展市场「按设备或引擎版本挑最新的兼容版本」未查，§4.2 的类比因此没有列进上表
